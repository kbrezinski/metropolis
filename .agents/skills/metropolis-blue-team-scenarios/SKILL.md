# Metropolis blue-team scenario audits

Run an exploratory, malware-inspired blue-team exercise on the selected testbed's declared design. Generate several potential paths where the evidence supports them, including paths stopped by controls, and record what defenders could test. This is a static scenario simulation, not evidence of infection. Do not invoke Codex Security scans, contact GNS3 or a compute, attempt logins, execute attack scripts or generated commands, or collect live host telemetry. Read relevant implementation code to explain intended firewall, service, and simulator behavior; do not turn this into a repository vulnerability scan. Offline validators and firewall-renderer checks may corroborate declarations when useful, but label them as offline. Do not describe a hypothetical compromise, installed rule, or physical effect as observed.

## Select and read the evidence

- Discover datasets under `testbeds/*/datasets/*` and catalogs under `scripts/attacks/scenarios/*.json`. Use the user's selections; select the only available choice when unambiguous. If several remain, ask which dataset or catalog to assess. Do not assume a fixed version, node count, address, or malware role.
- Treat the selected dataset's YAML in `topology/`, `device_instances/`, and `protocol_profiles/` as the source for declared assets, links, services, identities, and policy selectors. Read router configuration referenced by the selected infrastructure inventory, the firewall renderer and its application path, and only the device, broker, HMI, and SCADA code needed to check a proposed chain's behavior. Use the attack catalog to identify families and themes; bundled support nodes and attack actions do not prove an exploit works or fix the attacker's starting point.
- Keep evidence types distinct: declarations establish the intended network; renderer/router code establishes intended generated rules and routes; service code establishes conditional simulator behavior and possible logs; none establishes live deployment or exploit success. Use README prose, tests, and external projects only as leads to verify against the selected declarations or relevant code. Official ATT&CK and OWASP definitions classify steps, not Metropolis facts. Do not reproduce credential values, tokens, keys, or their hashes.
- In a full review, inspect declared service credentials for predictable patterns, reuse across nodes, and the scope of each identity or ACL. Report counts and relationships without values. A visual concern does not establish entropy, a successful login, or a running service.
- Record dataset and catalog paths, revision and review date, reviewed source hashes, and missing or contradictory inputs. Cite exact file paths and lines for every named node, address, service, network boundary, rule, command effect, and proposed observable. State the inference that connects evidence to each conclusion.

## Build the declared network view

Inventory hosts, roles, addresses, subnets, VLANs, links, switch port roles, router interfaces, routing and tunnels, service protocols and ports, identities, and firewall selectors. Build an asset/boundary view that a reader can trace into each scenario. Distinguish actual switch appliances from logical access segments, physical GNS3 links from logical overlays, and uncabled or spare declarations from attached hosts. A declared link is not proof of live cabling.

For each proposed source-to-destination hop, check its source subnet, local Layer 2 or routed path, router and tunnel settings, then the selected baseline firewall rule by source/destination CIDR, transport, and port. Read the renderer for default action, stateful return traffic, rule placement, and attack-only allowances; the YAML alone may not establish these. Same-VLAN traffic bypasses the routed firewall. Separate baseline rules from temporary experiment exceptions.

Mark the network path **permitted**, **blocked**, or **unknown under declared settings**, citing the decisive rule or missing evidence. An unmatched allow rule proves a block only when the generated policy also establishes default drop. Keep network permission separate from service availability, authentication, application authorization, command acceptance, and actuator confirmation. Never infer that declared routing, IPsec, ACLs, or firewall settings were applied in live GNS3. Flag conflicts between declarations and code rather than resolving them silently.

## Develop the scenarios

For a full review, screen every distinct family in the selected attack catalog, grouping entries from the same family. Explore plausible variants in foothold, target service, lateral or command-and-control route, and defender visibility, including a control-blocked branch where relevant. Select as many end-to-end chains as the evidence supports; do not force one chain per family or aim for a fixed count. The catalog is a seed, not a ceiling: label additional configuration-supported paths as outside the catalog. Treat malware names and bounded lab actions as behavioral inspiration, then screen every proposed hop against this testbed's topology and code. Record why a family was selected, screened out, or deferred. Bundled Mirai or Merlin support does not by itself establish infection or a working command-and-control or OT path.

For each chain, state an assumed internal foothold at T0. If external ingress is not declared, show an optional outside-to-foothold T-1 as unknown rather than inventing access. Use ordered T1–Tn stages, not invented elapsed times. Each hop names one source node, one destination node, their addresses, protocol and known source/destination ports (mark dynamic ports as such), network status, action, evidence, and remaining gate. Show acknowledgement and actuation as separate or branching events when their order is not guaranteed. A blocked or unknown hop cannot silently become a successful movement step.

Trace discovery, access, movement, command-and-control where relevant, command delivery, and possible OT effect. Explain why each transition follows from the cited configuration or code, including authentication, ACL, validation, feedback, and timing conditions. For each selected chain, state a testable defender hypothesis: the sequence that would support it, a gate or observation that would refute it, and a benign lookalike. Distinguish a reachable service from a demonstrated flaw. State the **simulator effect** supported by code separately from a **hypothetical physical implication**; do not infer hydraulics or water quality where the model does not implement them. Rank chains by declared reachability, extra prerequisites, and possible effect without numerical compromise probabilities.

Use current official [ATT&CK for ICS](https://attack.mitre.org/matrices/ics/) and [Enterprise](https://attack.mitre.org/matrices/enterprise/) tactics and techniques as prompts for malware behavior; relevant [software profiles](https://attack.mitre.org/software/) may suggest variants. Use the current official [OWASP OT](https://ot.owasp.org/) risk list for operational control questions and the [Web](https://top10.owasp.org/) or [API](https://api-security.owasp.org/) lists only for matching web or API surfaces. Abstract behaviors into this testbed's assets and boundaries; do not transplant product-specific exploits or imply that named malware is present.
Record a framework prompt separately from a supported mapping. Map ATT&CK techniques to hypothesized behavior only when the step fits the current official definition and testbed evidence; cite matrix and technique ID. Map OWASP categories to evidence-backed risk conditions on applicable OT, web, or API surfaces; cite project, edition, and category. A technique tag or risk category does not prove a flaw, attack success, or detection coverage. Leave unsupported mappings empty. Do not assign a CVE from a protocol or product name alone; require a supported product/version match and an authoritative advisory, otherwise state that no CVE was established.

## Coverage and defender observables

Give coverage explicit denominators in two ledgers: list every catalog family once, and separately list each relevant trust boundary or service path assessed. Cross-reference scenario IDs. Each row names assets/zones examined, selected/screened-out/deferred disposition, supporting evidence, reason, and missing verification. Include paths constrained by a control as well as plausible chains. Do not turn technique counts, catalog counts, or external projects' numerical detection scores into a Metropolis coverage percentage.

For each proposed defensive observable, identify the linked chain step, expected event or field, producing code/configuration, collection point (wire, device log, SCADA, broker, or host), and whether the telemetry is only declared, code-supported, offline-checked, or live-observed from user-provided evidence. Label it source-specific when emitted by reviewed code, or generic behavioral when only inferred. State a benign alternative or false-positive caveat. Correlate stages using IDs, source addresses, and time windows only when those data are actually available; prefer a supported behavior sequence over a lone IP, port, or signature. Missing telemetry is unknown, not a clean result. A proposed indicator is a detection lead, not attribution or a verified IOC. Do not import another project's fingerprints or run its host-triage commands.

## Deliverable

Give a short asset/trust-boundary summary and a baseline flow matrix covering relevant permitted, blocked, and uncertain paths. Include the coverage ledger, then a summary row per selected chain: family, assumed foothold, node-to-node path, possible simulator effect, and key gate. For each chain, state its testable defender hypothesis and framework inspiration separately from supported mappings. Give an ordered step table with one source → one destination, protocol/port, network status, action and prerequisite, evidence and inference, supported ATT&CK step mapping, and proposed defender observable with its collection point and caveat. List evidence-backed OWASP risk conditions separately. End with unresolved paths, telemetry gaps, and explicit live-verification limits.

## Save every review

By default, save each completed review under the repository's `scripts/agent-blue/<testbed>/<dataset>/<UTC timestamp>_<short Git revision>/`. Use a user-specified output root when provided. Create a new run directory each time; do not overwrite an earlier review or silently switch destinations if the chosen root cannot be written.

Write `scenarios.md` for human review and `scenarios.json` with matching scenario IDs, ordered steps, statuses, assumptions, defender hypotheses, framework prompts and supported mappings, coverage-ledger rows, and observable provenance/caveats. Write `review-metadata.json` with the selected dataset and catalog, UTC creation time, Git revision and dirty state when available, reviewed input paths and SHA-256 hashes, output paths, and completion or failure status. Use repository-relative output paths for the default location. Before completion, check that cited paths and line ranges exist, source hashes match, Markdown and JSON agree on IDs/statuses/coverage, and no credential values appear. If interrupted or unable to assess a family or boundary, retain partial files and mark the gap explicitly. Return links to the saved files.
