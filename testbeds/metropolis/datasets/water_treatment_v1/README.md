# Water treatment dataset v1

This directory holds the topology, device instances, protocol profiles, scenarios,
and metadata for one version of the water-treatment testbed dataset.

- `topology/` describes sites, subnets, links, routers, and switches.
- `topology/address-plan.yaml` records Metropolis v1's concrete network allocations using the repository-level `schemas/address-plan.schema.json` format.
- `topology/links.yaml` records the cabling, using `schemas/link-plan.schema.json`. It names the interface each router script configures, and the switch port roles from the switch specifications. Switch port roles are logical labels, not GNS3 port numbers: literal port numbers only become known once the project is cabled, so they are not asserted here. Unmanaged access segments are documented but not cabled, and every link is `planned` until someone cables and checks it.
- `topology/validation-report.md` is generated by `scripts/validate_metropolis_topology.py`, which cross-checks the address plan, inventory, link plan, router scripts, and switch specs. That script also validates every document on this list against its JSON schema in `schemas/`, and checks that all four declare the same `testbed_id`.
- `device_instances/` assigns addresses and roles to reusable models from `testbeds/metropolis/devices/`; `initial_devices.yaml` contains the PLC/RTUs, sensor, MQTT broker, SCADA, historian, HMI, engineering host, routine Modbus client, legacy Telnet gateway, DNS, and NTP nodes.
- `device_instances/infrastructure.yaml` lists the routers and switches. They are not Docker nodes, so they do not belong in `initial_devices.yaml`: a router is a VyOS appliance configured by a checked-in script, and a switch is a GNS3 Ethernet switch described by a specification document. Router interface addresses are repeated here on purpose so drift from the VyOS scripts is caught; unmanaged access switches are recorded as segments rather than invented as appliances.
- `protocol_profiles/` records protocol versions, endpoints, topics/register maps,
  and security settings.
- `scenarios/` describes normal operations and each experiment or attack run.
- `metadata/` records labels, capture points, timestamps, and run configuration.
- `captures/` is for generated PCAPs and other large outputs; its contents are
  excluded from Git.

Keep reusable device behavior and definitions under the top-level `testbeds/metropolis/devices/`
directory. A future dataset should get a new versioned directory under `testbeds/metropolis/datasets/`
with its own topology and device instances.
