# Water treatment dataset v1

This directory holds the topology, device instances, protocol profiles, scenarios,
and metadata for one version of the water-treatment testbed dataset.

- `topology/` describes sites, subnets, links, routers, and switches.
- `topology/address-plan.yaml` records Metropolis v1's concrete network allocations using the repository-level `schemas/address-plan.schema.json` format.
- `topology/firewall-policy.yaml` declares baseline routed flows by address-plan LAN or contained CIDR, protocol, and service port. A rule covers all hosts in the selected networks. `scripts/gns3/render_firewall.py --check` validates selectors and routes offline; the GNS3 router loader generates VyOS zone rules from this policy. Runtime enforcement is for the user to verify in GNS3.
- The six VyOS scripts use OSPFv2 area 0 for inter-router routing on transit links and the shared WAN. All connected device networks, including enterprise and attack-test, are advertised passively. Generated zone rules allow protocol 89 between declared router peers and retain default-drop restrictions for application traffic. Neighbor formation, route selection, and OSPF packets still need GNS3 verification.
- `topology/links.yaml` records the cabling, using `schemas/link-plan.schema.json`. It names the interface each router script configures, and the switch port roles from the switch specifications. Switch port roles are logical labels, not GNS3 port numbers: literal port numbers only become known once the project is cabled, so they are not asserted here. Unmanaged access segments are documented but not cabled, and every link is `planned` until someone cables and checks it.
- `topology/validation-report.md` is generated by `scripts/validate_metropolis_topology.py`, which cross-checks the address plan, inventory, link plan, router scripts, and switch specs. It validates the five topology documents against their JSON schemas and checks that they declare the same `testbed_id`.
- `device_instances/` assigns addresses and roles to reusable models from `testbeds/metropolis/devices/`; `initial_devices.yaml` includes four populated plant cells, two remote RTUs with their own networked level instruments and pump drives, four HMIs, services, and support nodes. Disinfection uses the existing VLANs 13 and 53. Central SCADA targets all four PLCs and both remote RTUs.
- Devices with no declared physical link are explicitly marked `link_policy: intentionally_uncabled` in the inventory. The standalone topology validator reports any other inventoried device without a link.
- `device_instances/infrastructure.yaml` lists the routers and switches. They do not belong in `initial_devices.yaml`: routers are VyOS appliances configured by checked-in scripts, and managed switches use the repository's Open vSwitch Docker image. Router interface addresses are repeated here so drift from the VyOS scripts is caught; unmanaged access switches are recorded as segments rather than invented as appliances.
- `protocol_profiles/` is reserved for protocol definitions. Current endpoints,
  topics, register maps, and settings live in device code and inventory.
- `scenarios/` is reserved for scenario definitions; attack entry points are
  currently under `scripts/attacks/`.
- `metadata/` is reserved for dataset metadata. Generated run details are
  recorded under `runs/<run-id>/` and `captures/<run-id>/`.
- `captures/` is for generated PCAPs and other large outputs; its contents are
  excluded from Git.
- `runs/<run-id>/logs/` holds normalized and raw Docker device logs plus
  router syslog for an experiment; `manifest.json` records collection and PCAP
  results, while `timeline.jsonl` holds run actions and project status. Matching
  PCAPs are in `captures/<run-id>/`. Runs are excluded from Git.
- `runs/<run-id>/features/raw/` holds per-capture packet CSVs generated from a
  completed `captures/<run-id>/manifest.json`; `features/extraction_report.json`
  records their provenance, counts, and failures. See `scripts/README.md` for
  the stage-one extraction command. No topology addresses are built into it.
- `runs/<run-id>/features/cleaned/` holds stage-two cleaned CSVs;
  `features/cleaning_report.json` records the exact rules, retained fields,
  row counts, hashes, and failures. The raw CSVs remain available.

Keep reusable device behavior and definitions under the top-level `testbeds/metropolis/devices/`
directory. A future dataset should get a new versioned directory under `testbeds/metropolis/datasets/`
with its own topology and device instances.
