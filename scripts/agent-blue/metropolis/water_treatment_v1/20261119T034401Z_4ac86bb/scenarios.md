## Network and trust boundaries

The address plan declares six process LANs (four plant VLANs plus reservoir and raw-water sites), five operations LANs, four HMI VLANs, and separate DMZ, enterprise and attack-lab LANs. Six VyOS routers and eight actual switch appliances carry those zones; thirteen named access segments are logical labels, not separately specified appliances. The plant and operations trunks carry their listed VLANs. Three physical /30 core transits connect the plant, DMZ and WAN routers. The shared `172.31.255.0/24` WAN is an underlay; operational routing to the remote sites is intended over logical IPsec VTIs with OSPF/BFD. VTI entries are not GNS3 cables. See `testbeds/metropolis/datasets/water_treatment_v1/topology/address-plan.yaml:7-208`; `testbeds/metropolis/datasets/water_treatment_v1/device_instances/infrastructure.yaml:16-245`; `testbeds/metropolis/datasets/water_treatment_v1/topology/links.yaml:19-323`; `testbeds/metropolis/router/backbone/router_ot_wan.sh:24-56`.

All links in the link plan are planned declarations, not verified live cabling (`testbeds/metropolis/datasets/water_treatment_v1/topology/links.yaml:5-14`). `MET-DEBUG-DMZ-01` is explicitly uncabled (`testbeds/metropolis/datasets/water_treatment_v1/device_instances/initial_devices.yaml:706-714`). The baseline firewall uses source and destination network selectors, usually entire LANs; the /32 SNMP rule is an exception (`testbeds/metropolis/datasets/water_treatment_v1/topology/firewall-policy.yaml:1-47`). Its selected YAML contains allow flows but no default action. Referenced router scripts say generated zone rules are added separately, while the rules themselves are absent from the selected configuration (`testbeds/metropolis/router/backbone/router_ot_dmz.sh:2-12`). Hence an unmatched routed flow is **unknown under declared settings**. Same-VLAN paths bypass the routed policy. Lab exceptions, when a run selects them, are separate from this baseline (`testbeds/metropolis/router/backbone/router_ot_dmz.sh:10-12`).
